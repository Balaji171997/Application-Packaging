**2026-07-18 (MTB r200 / GPF r15) — TWO share-launch regressions, both FIXED. Symptom: shortcut → ".pak not found", then German `…PackageBuilder.pak konnte nicht gefunden werden`.** The live share `\\mndemucfsm01\…\Balaji\PackageBuilder` DOES ship the pak `Hidden+ReadOnly` (contrary to the r144 note below that said the lock was removed — `Set-ToolVisibility` still hides it). Two required-file / code gaps:
1. **`PackageBuilder.exe.config` MUST sit next to the exe on the share.** It was missing → the ps2exe launcher couldn't resolve/load from the UNC path → Loader's "PackageBuilder.pak not found next to the launcher". It's the `<loadFromRemoteSources enabled="true"/>` + long-path `AppContextSwitchOverrides` config (identical copy lives in `Downloads\files` and `Downloads\GPF-PackageBuilder`). **Any share refresh must redeploy exe.config alongside the exe.** Now also in `Invoke-SelfStage`'s copy list so the local staged copy gets it.
2. **`Copy-IfNewer` (Core.ps1) used `Get-Item -LiteralPath $Source` WITHOUT `-Force`** → `Get-Item` THROWS "cannot find path" on the **Hidden** pak (unlike `Test-Path`, which finds hidden), so the self-stage crashed with that German dialog. FIXED: added `-Force` to both `Get-Item` calls on that line (MTB + GPF). Now hidden pak stages fine. Locked by a Test-Build assertion that sets the fixture pak `Hidden,ReadOnly` before `Invoke-SelfStage`. Deploy: backed up old pak `PackageBuilder.pak.bak-<ts>`, copied r200, re-applied `Hidden,ReadOnly` (safe now). See [[ps51-comma-arg-and-alias]] family for other PS 5.1 traps.

**2026-07-20 (MTB r210) — the exe.config gap RECURRED after the user deleted + recreated the share folder.** Symptom reported as a one-off ".pak not found in local directory". It was NOT transient: the recreated folder was missing `PackageBuilder.exe.config` again (also absent from the local portable `Downloads\PackageBuilder`). This is the SAME root cause as the 2026-07-18 note below. **Whenever the share folder is recreated/refreshed, re-check the required set** — quickest audit is to diff the file list against `Downloads\files`: `PackageBuilder.exe`, **`PackageBuilder.exe.config`**, `PackageBuilder.pak`, `settings.json`, `snippets.json`, `KnowledgeBase.Recommend.json`, `Lib\`. Both locations fixed.

**Pak-replacement must be near-ATOMIC.** `settings.json` has NO `UpdatePath`, so the Loader's self-update branch never runs — users launch the share exe and load whatever pak sits beside it, i.e. replacing the share pak IS the update mechanism. A plain `Copy-Item` over the live pak leaves a window where a launching user reads a TRUNCATED pak; that path is UNGUARDED (the friendly "not found" box only covers a missing file) and dies at `TransformFinalBlock`/Deflate with no message. **Use: clear attributes → back up → copy to `PackageBuilder.pak.new-<ts>` → `Move-Item` over the live name → re-apply `Hidden,ReadOnly`.** Rename is near-instant, so there is no partial-read window.

**2026-07-20 (MTB r211 / GPF r24) — SCCM actions on a machine that HAS the ConfigMgr console: "failed to connect to site" was a LIE.** Real log: `ConfigMgr console detected … using its module: C:\Program Files (x86)\Microsoft Endpoint Manager PreLive\bin\ConfigurationManager.psd1` → `Import ConfigMgr module failed: File …\AdminUI.PS.psm1 cannot be loaded because running scripts is disabled on this system.` So the failure was the MODULE IMPORT (execution policy), the site was never contacted, yet every caller reported the flat "Could not connect to the SCCM site." Three fixes in `Connect-Sccm` (BOTH tools — this is brand-agnostic infrastructure, not template):
1. **`Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force`** (best-effort, try/catch) BEFORE any Import-Module. Process scope = in-memory, no admin, no registry write, dies with the process. NOTE the tool's own engine is immune to execution policy because the pak runs via `[scriptblock]::Create()` from MEMORY — only on-disk `.psm1`/`.ps1` files are gated, which is why the tool runs fine but the module import dies. Only a GPO-set MachinePolicy/UserPolicy can defeat the process override; that case logs a clear warning.
2. **Bundled-module FALLBACK**: if the CONSOLE's module fails to import, fall back to the bundled `ConfigurationManagerPrelive` instead of `return $false`. `$installedMod` and `$bundledMod` are now resolved SEPARATELY so the fallback path exists. GPF's Connect-Sccm had NO console detection at all — brought in line with MTB.
3. **Honest errors**: new `$script:SccmConnectError` + `Get-SccmConnectMessage`; all 10 call sites changed from the flat literal to `Message=(Get-SccmConnectMessage)`, so the UI now names the real cause (module missing / import blocked / site drive unreachable).
CAVEAT: could NOT reproduce locally — AW140 has no console installed (`C:\Program Files (x86)\Microsoft Endpoint Manager*` absent) and 32-bit PS there reports Bypass, so the "x86 reads the WOW6432Node hive" theory is UNPROVEN. The fix targets the exact error text; verify on the console machine.

**CURRENT design (2026-07-01, r144) - SELF-STAGE with deferred modules:** users get a SHORTCUT to the SHARE's PackageBuilder.exe. On a network launch (`Test-NetworkPath`), the tool mirrors the CORE (exe, pak, 3 JSONs, AvalonEdit, icon, PSADT template) to `%LOCALAPPDATA%\PackageBuilder` via `Invoke-SelfStage` (Core.ps1), writes a `.source` marker, and RE-LAUNCHES the local exe (network ops need a LOCAL process). The heavy SCCM/Intune modules are NOT copied at launch - `Ensure-PublishModulesStaged` mirrors them share->local Lib ON DEMAND at first publish (both publish jobs call it; the Integration tab warms them in a background runspace). UPDATES: maintainer replaces the SHARE pak; each launch `Copy-IfNewer` pulls the newer pak to the local cache before relaunch (modules refresh newer-only on next publish). Disable via settings.json `"LocalRelaunch": false`. Full-local-copy still works (no network -> no relaunch; no `.source` -> `Ensure` no-ops because Lib is already complete). Prior sessions had a `/MIR`-everything-except-ConfigMgr relaunch (loaded ConfigMgr from share via `$env:PB_SHAREROOT`) - replaced by core-only self-stage; `PB_SHAREROOT` kept as a `Get-StageSource` fallback. exe.config + the hidden/read-only lock were REMOVED (not needed once running local).

**(Earlier interim decision, now superseded by self-stage):** users **COPY THE WHOLE FOLDER LOCALLY** and run PackageBuilder.exe from the local copy. The share-shortcut method was ABANDONED because running the exe directly from a UNC share breaks the network stack: SCCM `New-PSDrive` fails with "A non-recoverable error occurred during a database lookup" (WMI/DNS) and Intune fails (WinHTTP proxy "invalid argument" / token "error sending request"). Proven: whole folder copied local = both work; run-from-share = both fail, across machines, and NOT caused by the exe.config (SCCM failed from share before it existed). r143 added a zero-copy attempt (pin `[Environment]::CurrentDirectory` to $env:TEMP in GUI.ps1, since a UNC-launched process's CWD is the network path) - if that didn't fix the from-share case, copy-local is the answer (which the user chose). exe.config REMOVED from the distribution (loadFromRemoteSources only mattered for the share). All features enabled.

**Distribution structure + lock (`Set-ToolVisibility.ps1 -Hide -Path <folder>`):** the folder shows users ONLY `PackageBuilder.exe` + the 3 JSON configs (settings/snippets/KnowledgeBase). Everything else (PackageBuilder.pak, Lib\, template) is HIDDEN + READ-ONLY (read-only applied recursively to Lib files; the exe is visible+read-only; JSONs stay visible+writable). `-Show` reverses it (maintainer). Attributes survive an Explorer folder-copy. Order matters in the script: set Hidden BEFORE read-only or the stale-object attribute write clobbers read-only.

**Security reality:** the tool's LOGIC is ALREADY tamper-proof (AES-256 inside PackageBuilder.pak - users can't read or change behavior). Hidden+read-only only prevent ACCIDENTS on the exposed support files. On a user-owned local copy the user is owner and can override attributes; true enforced immutability needs a controlled SHARE with NTFS deny-write (which copy-local gives up). "Encrypted pak + read-only + hidden" is the practical ceiling and already protects the actual tool.

(Historical share idea, now abandoned: whole tool on a share, users get a shortcut; central JSONs.)

**Why a shortcut, not a bare exe:** the loader + engine resolve their root from the exe's OWN folder (`Loader.ps1` `$PSScriptRoot`/`MainModule.FileName`; `Core.ps1 Get-ToolRoot`). Root must contain PackageBuilder.pak, settings.json, snippets.json, PSADT_Template(.zip), Lib\ (AvalonEdit + MSAL.PS + IntuneWin32App + ConfigurationManagerPrelive). A bare exe copied elsewhere orphans it from all of that. A shortcut whose target is `\\share\...\PackageBuilder.exe` makes Get-ToolRoot resolve to the share -> everything found.

**What already works from a UNC share (verified by reading the code):** AvalonEdit loads via `[Reflection.Assembly]::Load([IO.File]::ReadAllBytes())` (load-from-bytes -> immune to the UNC/MOTW assembly block); all runtime output (logs/build/IntuneWin/temp + template-zip extraction) goes to LOCAL `C:\temp\PackageBuilder` (Get-WorkRoot), never the share; package output goes to the Outgoing shares; source fetch / icon extraction / doc folders / manual installer selection operate on source+output paths, not the tool root.

**Binary modules over UNC (CONFIRMED by the 2026-07-01 on-share test):**
- **Intune** `Import-Module MSAL.PS` FAILED from the share with "Cannot add type. Compilation errors occurred." (MSAL.PS compiles internal C# referencing its own DLLs; csc/CLR won't load them from a remote path). FIXED r141: `Intune.ps1 Get-LocalModuleManifest` copies a UNC module folder to a LOCAL cache (`Get-WorkPath 'modules'`) and imports from there (MSAL.PS before IntuneWin32App). Local paths pass through. So Intune now works from the share.
- **SCCM** ConfigMgr module IMPORTED fine from the share (pre-compiled DLLs load from an intranet share). Its failure "New-PSDrive G08: A non-recoverable error occurred during a database lookup" is the SMS Provider host (`mbdcaswvtb29843.mn-man.biz`) NOT RESOLVING/reachable from the machine = network/DNS/VPN/rights, NOT a tool bug. Verify `nslookup` the SiteServer, VPN, settings.json `Sccm.SiteServer`, SCCM rights.
- `PackageBuilder.exe.config` (`<loadFromRemoteSources enabled="true"/>` + long-path AppContextSwitchOverrides) ships next to the exe; harmless locally.

**BIGGER ROOT CAUSE (2026-07-01, r143) - "works copied-local, FAILS from share shortcut" on the SAME machine (user has SCCM rights, console works):** launching the exe from a UNC share runs it in the RESTRICTED NETWORK ZONE - CAS sandboxes arbitrary NETWORK ops. So SCCM (WMI+DNS to the site server -> "A non-recoverable error occurred during a database lookup") and Intune (HTTPS + GetSystemWebProxy -> "invalid argument" -> "error sending request") FAIL; FILE I/O still works (package creation, module staging succeeded from the share). It is NOT DNS/VPN/rights - it is the launch ZONE. TWO fixes: (1) shipped r143 - GUI.ps1 detects UNC $root, robocopy-mirrors the tool to %LOCALAPPDATA%\PackageBuilder (excludes the huge ConfigMgr module; $env:PB_SHAREROOT lets Connect-Sccm still import it from the share), relaunches the LOCAL exe (full trust) and Exit(0)s the share instance - users still hold only a shortcut; best-effort fall-through. (2) DEFINITIVE / if the relaunch can't fire: add the share host to the LOCAL INTRANET zone (GPO Site-to-Zone `file://mndemucfsm01`=1, or reg `HKCU\...\Internet Settings\ZoneMap\Domains\mndemucfsm01` `file`=DWORD 1) -> share becomes full-trust like local. Disable the relaunch via settings.json `"LocalRelaunch": false`.

**Snippets = TEAM-SHARED (2026-07-01, user chose):** `settings.json -> SnippetsPath` is set to the shared `snippets.json` on the share (`\\mndemucfsm01\...\Balaji\PackageBuilder\snippets.json`). The tool (GUI.ps1 ~1585) reads AND writes snippets there, so ANY user's added snippet lands in the shared library and everyone gets it next launch. Even though the tool runs locally (self-stage), SnippetsPath is an absolute UNC path so the local process reads/writes the share file directly. `Save-SnippetsModel` is concurrency-safe (temp file in the SAME folder -> atomic `[IO.File]::Replace` with 5 retries, so two users saving at once don't corrupt it). REQUIREMENT: the shared snippets.json + its folder must be WRITABLE by the whole team; if not, users can read but Save fails gracefully (warning) - then point SnippetsPath at a team-writable share path. settings.json is external (not in the pak) so this needed no repack; the self-stage copies the updated settings.json to users on next launch.
