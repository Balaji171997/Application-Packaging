**v3→v4 conversion bug (found on MTB DSA_PRODISAuthoring, reported 2026-07-22; fixed r214 / GPF r27).** v3's `Get-InstalledApplication` (and `Remove-MSIApplications`) accepted the app NAME as a POSITIONAL argument — its `-Name` was `Position 0`. So real scripts wrote `Get-InstalledApplication -WildCard '*CodeMeter Runtime Kit*'` or `Get-InstalledApplication '*X*'`. Our converter renamed the cmdlet + swapped the `-WildCard`/`-Exact`/`-RegEx` SWITCH to `-NameMatch '<value>'`, giving `Get-ADTApplication -NameMatch 'Wildcard' '*CodeMeter Runtime Kit*'`.

**Why it broke:** in v4 `Get-ADTApplication`/`Uninstall-ADTApplication`, `-Name` is `[Parameter(Mandatory=$false)]` with NO Position, and **Position 0 is `-FilterScript` (a `[ScriptBlock]`)**. So the bare name string binds to `-FilterScript` → the call errors / matches nothing. Verified against the bundled PSAppDeployToolkit.psm1 (`-NameMatch` ValidateSet = `Contains`/`Exact`/`Wildcard`/`Regex`, case-insensitive so `'WildCard'` still binds — casing was NOT the bug; the missing `-Name` was). User's working hand-fix: `Get-ADTApplication -Name '*CodeMeter Runtime Kit*' -NameMatch WildCard`.

**Fix:** new `Add-AdtApplicationNameParam` (PSADT_V3toV4_Mappings.ps1, called last in `Convert-V3ToV4Content`, BOTH tools — standard PSADT, not brand-specific). Per `Get-ADTApplication`/`Uninstall-ADTApplication` call: skip if `-Name` or `-ProductCode` already present; else mask the `-NameMatch <val>` pair, find the first remaining quoted-string OR `$var` positional, and insert `-Name ` before it. Output is `-NameMatch 'WildCard' -Name '*X*'` (named params are order-independent; both forms valid). 5 Test-Build asserts each (positional gains -Name, keeps NameMatch, exactly ONE -Name, output PARSES, ProductCode lookup gets NO -Name). MTB 485/0, GPF 547/0.

**Also confirmed CORRECT (no fix needed):** `Invoke-ADTAllUsersRegistryAction -ScriptBlock { ... $_.SID ... }` is exactly what v4 documents (`-ScriptBlock` is Position 0; `$_.SID` inside the block per the module's own .EXAMPLE). `Convert-HKCUAllUsers` already turns the v3 `[scriptblock]$HKCURegistrySettings = {...}` + `Invoke-HKCURegistrySettingsForAllUsers -RegistrySettings $var` + `$UserProfile.SID` into that inline form. The v3 variable-form the user tried does NOT work on v4 (renamed fn + `$UserProfile` doesn't exist) — that's expected, our inline output is the right shape.

**DONE — the tangled if/else was a REAL reuse-engine bug (user confirmed fresh tool output, no edits). Fixed r215/r28.** `Find-ExistingUninstallBlock` (Build.ps1) matched ANY `If (...Get-(ADT|Installed)Application...)` and excised it as a predecessor-uninstall block, so it ate the CodeMeter DEPENDENCY GATE `if(!(Get-InstalledApplication '*CodeMeter Runtime Kit*')){Exit-Script}else{...}`, stripping the `if{}` and orphaning the `else` onto the next (real predecessor) block.   2. **No else/elseif** branch (a real uninstall is a plain `If(installed){remove}`; if/else is conditional logic — keep in ALL cases).
  3. **Refers to OUR predecessor**: its `-Name` fuzzy-matches our app (via `Get-PBNormToken` = strip non-alphanumerics, lowercase, so `PRODIS.Authoring`≈`PRODISAuthoring`) OR the block carries our `VWG\CM\<Vendor_App>` branding key. A block that NAMES a DIFFERENT app (VC++/.NET) with neither is KEPT. A **ProductCode-only** block (no `-Name`) stays excisable (version-specific real uninstall). A matching branding key forces removal regardless of name.
